# AGENTS.md

VíaLibre — employability platform. Monorepo: 3 FastAPI microservices (auth, core, match) + Next.js 14 frontend, one PostgreSQL DB split into 3 schemas, one Nginx gateway. Orchestrated with `docker-compose` and a `Makefile`.

## Layout

- `services/{auth,core,match}-service/app/` — each service has `config.py` (settings + its own `schema_name` / `api_v1_prefix`), `database.py`, `models/`, `schemas/`, `api/v1/endpoints/`
- `shared/python/vialibre_common/` — JWT verification, shared enums, minimal PDF generator. Installed into every container at `/shared` (on `PYTHONPATH`) and bind-mounted
- `frontend/` — Next.js App Router under `src/app`, TypeScript path alias `@/*` → `src/*`
- `gateway/nginx.conf` — `/api/v1/{auth,core,match}/` → services; everything else → frontend

## Commands

Everything goes through Make + `docker-compose` (v1 syntax). The stack must be up first.

- `make up` / `down` / `logs` / `ps` — lifecycle (`logs-auth`, `logs-core`, `logs-match` per service)
- `make clean` — `down -v`, **wipes the DB volume**
- First run: `make up`, then `make setup-db` (= `init-schemas migrate seed seed-core seed-match`). Schemas must exist before migrations.
- `make migrate MSG=descripcion` — autogenerate + upgrade on all 3 services (`migrate-auth`/`-core`/`-match` for one)
- Frontend (from `frontend/`): `npm run dev` / `build` / `lint`
- Ports: nginx `80`, frontend `3000`, auth `8001`, core `8002`, match `8003`, Postgres on host `5433`

## Database & migrations

- One database `vialibre`, three schemas: `vialibre_auth`, `vialibre_core`, `vialibre_match`. Each service owns exactly one schema.
- Alembic revisions are **autogenerated and gitignored** (`services/*/alembic/versions/`). Don't hand-write or expect committed revision files; run `make migrate-<svc>`. Version tables: `alembic_version_auth/_core/_match`.
- Each `alembic/env.py` uses `include_name` to restrict autogenerate to its own schema — without it, migrations recreate everything and try to drop other services' tables.
- When adding a model, import it in that service's `models/__init__.py` **and** `alembic/env.py` or autogenerate won't see it.
- Seeds are idempotent and use fixed UUIDs shared across services (a company created by the auth seed is referenced by the core and match seeds). Keep those UUIDs in sync. Demo logins are in `services/auth-service/app/seed.py`.

## Gotchas

- `database_url` hardcodes host `postgres` (docker network). Services can't run directly on the host — run them in containers.
- Cross-service calls are plain HTTP via `httpx` to `settings.auth_service_url` / `core_service_url`. Cross-service references (`author_id`, `solucionador_id`, `challenge_id`) are bare UUIDs with **no FK constraints**.
- Enum trap: `shared/python/vialibre_common/schemas.py` defines English `ChallengeStatus`/`InteractionStatus`/`DifficultyLevel`, but each service defines and uses its **own** local Spanish enums (core: `abierto`/`en_progreso`/`cerrado`; match: `pendiente`/`aprobado`/`rechazado`). Edit the local model enum, not the shared one.
- Collection routes are registered without a trailing slash (`@router.post("")`), not `/`. This avoids the 308↔307 redirect loop through the Next.js proxy when companies publish.
- Shared lib code is bind-mounted (restart the service to pick up changes), but dependencies are baked into the image — run `make build` after changing any `requirements*.txt`.

## Frontend / auth

- `next.config.js` rewrites `/api/:path*` → `http://nginx:80/api/:path*`. Default API base is `/api`.
- The JWT is stored in a cookie (`AUTH_COOKIE_NAME`) and route protection lives in `frontend/src/middleware.ts` (`PROTECTED_PATHS` / `AUTH_PATHS`).
- API client wrapper: `frontend/src/lib/api.ts` (auth, challenges, interactions, reactions, file uploads/downloads).

## Testing

No test suite, Python linter/formatter config, or CI exist. The only available lint is `npm run lint` in `frontend/`. Verify backend changes by exercising the endpoints against the running stack (e.g. `/health` on each service).

## Local skills

Project skills live in `.opencode/skills/<name>/SKILL.md`. OpenCode 1.18.33 discovers them on session start (it scans `.opencode/{skill,skills}/**/SKILL.md`) and exposes them to agents through the native `skill` tool, which loads the full instructions on demand by exact name. The skills are additive: they describe *how* to extend the existing platform without rebuilding it.

- `codebase-audit` — read-only audit of architecture, features, dependencies and data model before touching code.
- `auth-rbac-security` — role/permission authorization, admin-only access, least privilege, endpoint protection and unauthorized-access tests.
- `database-design` — evolve the data model reusing existing entities, avoiding duplication, keeping integrity and safe migrations.
- `admin-dashboard` — administrative UI consistent with the existing Next.js frontend (tables, filters, forms, states, accessibility).
- `document-automation` — institutional DOCX templates, format preservation, editable output, autosave, versioning and secure storage.
- `testing-and-quality` — functional, integration, security and regression testing with real, documented results.

After editing any SKILL.md, restart the OpenCode session for changes to take effect (skills are loaded at startup).
